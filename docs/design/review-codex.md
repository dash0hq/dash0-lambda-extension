# Adversarial review of central masking

Verdict: **disagree with adopting option (c) as currently specified; agree with its export hook after the changes below.** It really can avoid an additional protobuf decode/encode, and the receiver really is on the normal instrumented invocation's response path. Those advantages do not establish either negligible cost or a complete disclosure boundary. Keep distro masking during migration and make the exporter a mandatory, bounded, fail-closed boundary before removing it.

Reviewed the analysis and draft plan against this worktree on 2026-10-23. References below use repository-relative `file:line`; ranges identify the relevant implementation. This was a read-only review except for this report: no source changes, dependency installation, deployment, or benchmarks. Cost figures below are explicit sensitivity estimates, not measurements of this extension.

## Objections, ranked by severity

1. **Critical — “never leaves the sandbox” is already false when diagnostic logging is enabled.** `src/otlp/logs_receiver.rs:20-24` logs the raw OTLP body at **info**, `src/otlp/receiver.rs:24-28` does so at trace, and `src/extension/telemetry_receiver.rs:25-31,75-81` logs full Telemetry API batches at info. Protobuf is not encryption: its string fields remain readable in lossy UTF-8 output. A Java log containing an authorization header can therefore reach extension stdout before any export-time processor sees it. AWS sends extension logs to CloudWatch independently of the Dash0 exporter ([Extensions API documentation](https://docs.aws.amazon.com/lambda/latest/dg/runtimes-extensions-api.html)). The default level is warn (`src/config/user.rs:87-90`), so this is configuration-dependent, not an unconditional default leak. Enabling info to diagnose an incident is nevertheless a supported and plausible trigger. Disabling collection of extension logs into Dash0 at verbose levels (`src/extension/register.rs:193-199`) does not disable CloudWatch delivery.

   **Change:** remove raw-body diagnostics from all three receivers before disabling distro masking. Log lengths/counts and parser error categories only. Test stdout as well as outbound OTLP using sentinel secrets at info and trace. Scope the guarantee to extension-controlled telemetry egress: original handler responses are intentionally forwarded unchanged (`src/extension/runtime_proxy.rs:203-204`), and application-owned exporters/logging are outside this boundary. A process crash does not by itself send its heap anywhere; distinguish that from a pre-crash log disclosure.

2. **High — the tolerant masking algorithm is a missing security component, not an existing reusable solution.** `src/otlp/masking.rs:108-117` returns malformed JSON unchanged. `src/util/truncate.rs:21-42` records only **closed** string literals; `:47-53` classifies keys by a following colon. It neither decodes escaped key names nor identifies an unterminated secret value. Reusing it as the proposed masker will miss a body cut after `{"password":"secret-prefix`, and a raw-text key matcher can miss JSON escape sequences in a key such as `pass\u0077ord`. Matching keys also requires correct handling of nesting, arrays, duplicate keys, primitive values, and quoted delimiters. A complete JSON parse followed by an independent naive scan is not a correctness argument.

   HTTP payload logs make the gap immediate. `src/otlp/span_mutations.rs:331-359` clones the first matching body attribute, builds its log, and removes the body attributes. `src/otlp/log_mutations.rs:179-181,224-226` converts malformed JSON into a `Value::String`. Merely invoking recursive key masking on that already-parsed value leaves the entire truncated body untouched. Form bodies have the same issue. Thus the draft's HTTP-log exception needs a format-aware string path as well as object traversal. Duplicate HTTP body attributes are removed after only the first is captured: existing data loss, not proof of masking completeness.

   **Change:** define conservative behavior for every supported format before moving responsibility. An ambiguous/truncated payload whose safe masking cannot be established should be replaced or dropped, with a count and reason, rather than exported unchanged. Specify escaped keys, cut values, percent-encoded query/form names, repeated parameters, and encoded delimiters; recognize a format before decoding it so literal `+` and URL structure are preserved. Fuzz the scanner and explicitly test secret prefixes. Apply the same policy in `build_payload_body` **before** rendering/truncation, including its string fallback. `all` must replace before parsing; `none` should bypass traversal.

3. **High — shutdown flushing has no usable deadline discipline, and skips failure shutdowns.** `src/extension/events.rs:90-105` flushes SHUTDOWN only for `spindown`, then spends 200 ms waiting before sequential export. `TIMEOUT` and `FAILURE` do not take this path. `deadlineMs` is not read (`:210-226`). The draft's “500 ms for internal/managed shutdowns” conflates categories: AWS documents 500 ms with internal extensions and 2,000 ms with external extensions; Dash0 is an external extension. Reset after invocation failure is also a shutdown scenario, not a promised new 500 ms masking window ([AWS lifecycle documentation](https://docs.aws.amazon.com/lambda/latest/dg/lambda-runtime-environment.html)). Use the supplied deadline, not an assumed full allowance.

   The defaults are 2,000 ms per attempt and one retry (`src/config/user.rs:42-53`). A single timed-out send can consume 4 s; the four sequential nonempty exports—traces, OTLP logs, telemetry logs, metrics—can consume approximately **16 s plus CPU and the 200 ms sleep** (`src/otlp/exporter.rs:21-34,305-327`). Even the first 2 s attempt cannot fit after the shutdown sleep. Masking takes place before the timeout around `client.request`, so this timeout does not bound parsing, masking, protobuf encoding, or gzip. Adding an outer Tokio timeout alone does not preempt a long synchronous masking pass.

   **Change:** pass an absolute deadline through flush/build/send; calculate retries and each attempt's budget from remaining time, reserve termination margin, and remove or clamp the fixed shutdown sleep. Bound record size, total batch size, and synchronous processing chunks. Attempt bounded cleanup for TIMEOUT/FAILURE when feasible, while explicitly documenting that SIGKILL/OOM cannot guarantee delivery. Never fall back to sending an unmasked batch to meet a deadline. If out of budget, drop unsanitized records and count the loss when possible.

4. **High — flush-before-freeze is not a barrier for all producers.** In the default mode, `src/extension/telemetry_receiver.rs:46-49` sends the runtimeDone notification **before** storing the batch's logs (`:65-67`), and before its error branch constructs/sends synthetic traces (`:83-106`). `src/extension/events.rs:125-132` can wake and drain concurrently. The runtime proxy also forwards the response before building its return log and updating stored trace errors (`src/extension/runtime_proxy.rs:204-226`). A runtimeDone can therefore race with that proxy tail. Multi-threaded Tokio tasks make these real ordering possibilities (`src/main.rs:52,106-128`). The exporter may take a trace before `apply_return_value_error_to_stored_traces` can amend it (`src/otlp/span_mutations.rs:641-666`).

   Scenario: runtimeDone arrives, the event task drains logs, then the telemetry handler appends the late batch; the event task calls Next and the sandbox freezes. Late data waits for another invocation or spindown and can be lost on reset. There is also one global, unkeyed oneshot (`src/state/invocation_data.rs:95-104`): runtimeDone arriving before notifier registration is not remembered, and an old delayed event is not checked against the awaited invocation. The 900 s timeout/closed-channel branches only log; they do not flush (`src/extension/events.rs:118-145`). Export masking remains safe for batches that pass its gate, but does not solve these lifecycle races or guarantee seeing “every span of the invocation at once.”

   **Change:** make completion durable and keyed by invocation ID; register/observe it without a lost wakeup. Store and finish constructing telemetry before publishing completion, and synchronize response-tail mutations with the final drain. Serialize or otherwise coordinate error-triggered exports with normal flushes. Test these schedules with barriers rather than sleeps. Do not hold the invocation-store mutex while running masking or network operations.

5. **High — (c) is not free of response-latency impact in deferred mode, and payload masking explicitly remains on receive.** With `DASH0_SEND_ON_INVOCATION_END=false`, `src/extension/events.rs:90-105` sleeps 20 ms and flushes when the next INVOKE arrives. The new handler can run concurrently, but both processes consume the same CPU and memory allocation. A 128 MB CPU-bound handler competing with a large JSON masking batch can finish later; “CPU contention, not blocking” still changes caller latency. A synchronous pass can also occupy a Tokio worker serving the runtime proxy/local OTLP endpoint. For true mode, a successful ordinary runtimeDone places export after runtime response completion, so the direct response-path advantage is real; longer extension work still extends billed execution and delays reuse of that environment. Payload-log masking inside `build_payload_body` still runs before the OTLP receiver's 200 (`src/otlp/span_mutations.rs:343`, `src/otlp/receiver.rs:36,130`). It costs traversal, regex matching, and replacement allocations, not just a constant number of “key checks.”

   **Change:** describe the promise as “no additional synchronous span/OTLP-log masking in the normal response path,” with explicit exceptions and a separate latency budget for false mode. Measure caller p95/p99, next-invocation latency, billed duration, and extension CPU at low memory. Preserve an early masking option for workloads whose privacy/retention requirements outweigh the measured latency difference.

6. **Medium — no additional protobuf round trip is correct, but the allocation/cost claims are understated.** `src/otlp/exporter.rs:187-205,146-162` already decodes stored protobuf, combines owned resources, then encodes once. An in-place traversal inserted there needs **zero additional protobuf decodes or encodes**. Do not implement it by encoding the request and calling a byte-oriented masking helper. However, an OTLP `StringValue` holding JSON is not a parsed JSON tree. `serde_json::from_str` allocates a second representation, key matching visits it, and changed attributes require a new serialized string. The existing helper always serializes valid JSON, even with no match (`src/otlp/masking.rs:111-115`); avoiding that requires a changed flag or another implementation. URL/form decoding, replacements, fallback scanning, and recursion all have additional costs. A malformed JSON strategy that first parses then scans can read much of the same payload twice.

   Existing peak memory already includes the retained stored protobuf bodies and the merged decoded request, then output protobuf (`src/otlp/exporter.rs:188-205,402-422`). Parsing one attribute at a time bounds additional tree memory by the largest attribute; parsing every attribute into temporary trees first would scale it by the entire batch. Illustrative allocator sensitivity: a 1 MiB JSON attribute at 2–10 times input size in tree/string/node storage adds 2–10 MiB; a 10 MiB aggregate processed all at once could add 20–100 MiB. These multipliers are not measured, and small-key JSON can be worse. That is material at 128 MB shared with the runtime. Gzip creates another buffer and every HTTP attempt clones the transmitted body (`:288-303,308`). These are baseline costs, not new protobuf work attributable to (c).

   **Change:** mask one owned attribute at a time, compile rules once, fast-dispatch exact recognized attribute names, use bounded scanners, serialize only changes, and drop old strings promptly. Record peak RSS and allocations as well as elapsed time. Do not attribute the existing redundant Node JSON-to-protobuf encode (`src/otlp/receiver.rs:64,66`; `src/otlp/span_mutations.rs:816`) to (c), or claim it has disappeared.

7. **Medium — “gzip and network dominate” is an unmeasured workload assumption.** Gzip is optional (`src/config/user.rs:63-66`), level 3 runs synchronously (`src/otlp/exporter.rs:382-388`), and neither its duration nor masking is included in the current send timing, which starts at `:322` after request construction. A nearby endpoint with a warm connection may cost little; many tiny keys can make regex/object traversal expensive while repetitive JSON compresses cheaply. Masking can also reduce output size and gzip work, so the net cost is not a fixed surcharge.

   A useful estimate is `Tmask_cpu ≈ B/S + K×Cmatch + replacement/serialization cost`, where B is inspected payload bytes, K is inspected keys, and S is effective scan/parse throughput. With eight default regexes (`src/otlp/masking.rs:15-24,84-85`), 10,000 nonmatching keys can require 80,000 regex searches. Custom rule count and key length also matter; Rust regex avoids classic exponential backtracking but does not make an arbitrary number of searches free.

   For sensitivity only, if the **whole masking pass** achieved 25–250 MiB/s on one vCPU, 1 MiB would cost about 4–40 ms of CPU. AWS allocates CPU proportionally to memory, with one vCPU equivalent at 1,769 MB ([AWS memory configuration](https://docs.aws.amazon.com/lambda/latest/dg/configuration-memory.html)). A simple sustained-credit model gives multipliers of approximately 13.8 at 128 MB, 6.9 at 256 MB, and 3.45 at 512 MB: approximately **55–553 ms**, **28–276 ms**, and **14–138 ms** respectively for that same hypothetical pass. This is not an AWS scheduling guarantee or benchmark; bursts, runtime contention, architecture, and key density change it. A 10 MiB backlog scales these CPU estimates by ten and can exhaust shutdown time even with a fast network. Comparing with an assumed 10 ms network request yields the opposite result to comparing with a 100 ms request.

   **Change:** remove the dominance assertion until measured. Benchmark JSON object/array/string, headers, URL/form, malformed/truncated payloads, all/no/sparse matches, many short keys, and custom regex lists. Use 4 KiB through 1 MiB attributes and multi-MiB batches on arm64/x86_64, 128/256/512/1,769 MB. Separate decode, mask, encode, gzip, network, retries, RSS, and end-to-end wall time; test gzip disabled too. Criterion on a developer CPU alone cannot validate fractional-vCPU Lambda tail latency.

8. **Medium — loss and retention are not made safe by moving masking into the exporter.** The exporters drain before processing or sending (`src/otlp/exporter.rs:21-23,38,80`; `src/state/invocation_entry.rs:301-310,352-358`), ignore final send errors (`src/otlp/exporter.rs:76,93-100,177-184`), and skip undecodable items (`:410-419`). There is no durable/requeue mechanism. A timeout, crash, or OOM after drain can lose an entire batch. This is mostly pre-existing, but adding CPU/allocation increases the exposure window.

   `delete_done_invocations` first removes empty Done entries, then evicts the oldest entries regardless of pending state or buffered content when more than ten remain (`src/state/invocation_entry.rs:371-405`). Normally traces/logs were already drained, but producers can append after a drain and before cleanup; those late records can be evicted. Ten entries is not a byte cap: a single invocation and the global OTLP log vector can grow substantially (`src/state/invocation_entry.rs:341-348`; `src/state/invocation_data.rs:22-35`). Option (c) retains raw telemetry for the whole deferred interval and raw copies are not zeroized when dropped.

   **Change:** document at-most-best-effort delivery separately from redaction correctness; add byte/record limits and explicit drop counters. If retries across flushes are wanted, retain only sanitized batches in a bounded queue and design ordering/deduplication. Do not requeue raw serialized batches on an error path that can bypass masking later. Exclude active entries from blind eviction, or account explicitly for every dropped buffered record.

9. **Medium — a central location does not define complete coverage or compatible rules.** `build_logs_request` and `flush_telemetry_logs` are separate pipelines (`src/otlp/exporter.rs:31-34,37-76,146-162`). Error-triggered `send_traces` (`src/extension/telemetry_receiver.rs:103-106`), supplementary/synthetic spans, OTLP log bodies, resource/scope attributes, span events/links, and captured handler/root attributes need an explicit scope decision. A walk of `span.attributes` plus `LogRecord.attributes` cannot justify a general claim about log bodies or every possible copy of a secret. The payload hook is necessary because mapping telemetry logs mostly clones their already-rendered string (`src/otlp/log_mutations.rs:289-296`). Handler attributes are cached and copied for supplementary spans (`src/state/invocation_entry.rs:225-241`); sanitize every final constructed span, not only originally received ones.

   Rule fallback is also less uniform than the draft says: malformed JSON rule lists fall back, but invalid regexes are silently skipped (`src/otlp/masking.rs:29-33,43-55`), and empty env-var rules fall back to general rules (`:128-132`). JSON string content inside a JSON string value is not recursively decoded by today's `mask_value` (`:88-105`). Resolve these distinctions before claiming shared semantics or removing earlier masking.

   **Change:** enumerate every controlled egress path and exact field/format scope, including intentional exclusions. Use one shared masking implementation with typed adapters for all final requests; allow the receive-time payload adapter to reuse it. Test accepted configurations and invalid patterns, explicit empty lists, `all`, `none`, nested JSON strings, SDK-truncated data, and copies in synthetic/root spans. Keep privacy examples/defaults/support tables synchronized in the implementation change as required by AGENTS.md.

## Freeze, shutdown, and failure outcomes

Freeze suspends memory and execution; it does not automatically export raw data. Termination discards volatile state. A correct mandatory pre-serialization sanitizer should never “flush raw to save data” in either situation.

| Situation | Current behavior / consequence for (c) |
| --- | --- |
| `SEND_ON_INVOCATION_END=true`, successful ordered runtimeDone | Event task awaits trace/log/metric exports before the next Extensions API Next (`events.rs:125-132`; `main.rs:134-136`). A sanitizer in final builders runs before their outbound request. Late producers and notifier races remain as objection 4 describes. |
| `SEND_ON_INVOCATION_END=false` | Next-invocation flush runs after the next INVOKE and 20 ms delay. After that flush, the event task may call Next while the current runtime is still executing; its new telemetry remains raw until another flush. Freeze can preserve it for an arbitrarily long idle interval. If no next invocation arrives, normal spindown is the remaining best-effort path. Trace draining does not exclude the new invocation, unlike telemetry-log draining (`events.rs:104-105`; `exporter.rs:21-23,31-38`). |
| SHUTDOWN/SPINDOWN | Both modes enter the same sleep/flush path; no deadline propagation and overly long retries. Partial delivery followed by SIGKILL is possible. A gate protects whatever is sent; it does not guarantee everything is sent. |
| SHUTDOWN/TIMEOUT or FAILURE | `flush_if_needed` skips export. Error telemetry may independently trigger trace/telemetry-log export (`telemetry_receiver.rs:75-106`), but that does not guarantee receipt/order or flush OTLP logs and metrics. A surviving extension cannot depend on this rescue path during OOM/reset. |
| Missing/early runtimeDone; notifier closes | Default wait can last 900 s and then does not flush. Invocation timeout/reset may intervene much earlier. No masking-completion guarantee follows from this timeout. |
| Eviction, parse failure, exhausted retries, panic/OOM | Volatile data can be dropped, including unmasked data that never reaches a sanitizer. This is loss, not an inherent outbound disclosure. Diagnostics or an unsanitized fallback are separate disclosure paths and must be forbidden. |

AWS freezes an environment after runtime and extensions complete, and the next-event calls signal lifecycle progress ([execution environment lifecycle](https://docs.aws.amazon.com/lambda/latest/dg/lambda-runtime-environment.html)). “Awaited before Next” is necessary for the event task's own flush, but insufficient for independent telemetry/runtime-proxy tasks. It is especially unsafe to introduce a background masking task without including it in a producer-completion barrier.

## Attack on the alternatives and recommended decision changes

| Option | Strongest objection | What would make it defensible |
| --- | --- | --- |
| (a) Receive-time masking | Adds to the confirmed synchronous flush path and repeats work for attributes later copied into supplementary spans or discarded. It still needs the same correct malformed-data policy and cannot by itself sanitize attributes created later in the proxy. | Useful as a measured privacy-first mode, with in-place processing on existing decoded requests and a final egress check for later additions. It reduces raw retention; it does not eliminate original request buffers or language-runtime copies. |
| (b) Ack then background work | ACK means accepted data is only volatile; task ownership, response-tail mutation ordering, freeze, and shutdown cancellation become harder. Spawned work is not a free CPU pool. | Move owned decoded requests rather than encode/decode them again; use bounded queues, backpressure, keyed completion, and await/drain every producer before Next. The draft's extra protobuf round trip is not intrinsic if decoded ownership is transferred, but the refactor is substantial. No reason to add this machinery solely for masking. |
| (c) Final decoded-request masking | Keeps secrets longer, concentrates JSON CPU/allocations near export deadlines, and requires coverage of multiple final builders plus the early HTTP-payload path. | Retain its zero-extra-protobuf hook, but require the nine changes above, bounded best-effort delivery, and measured latency/memory budgets. |
| (d) Distro masking | Costs runtime CPU, has divergent semantics, and cannot protect arbitrary SDK-emitted telemetry or fields subsequently created in the extension. | Retain temporarily as defense in depth. Remove per runtime only after parity/coverage and malformed/truncated-data tests pass; compare the **net** cost of removed distro work against added extension work. |

Recommended decision: **keep (c) as the candidate architecture, not an approved implementation plan.** First remove raw diagnostic sinks and specify fail-closed coverage; then implement the shared masking logic at final decoded builders and before HTTP payload-log rendering; then add lifecycle/deadline discipline and run low-memory Lambda measurements. Establish separate acceptance gates for redaction completeness, loss behavior, memory, billed duration, and caller latency. Neither freeze nor successful SDK forceFlush proves durable delivery, and neither a shared Rust implementation nor an existing protobuf decode proves negligible masking cost.
